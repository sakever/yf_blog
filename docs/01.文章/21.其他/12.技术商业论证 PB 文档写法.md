Product Brief 是问题导向的轻量决策文档，回答的是“为什么值得做”，通常在正式 PRD 或技术方案之前使用。面向 CTO 的 PB，尤其需要克制：不展开 UI 细节、不陷入按钮文案、不提前承诺具体实现方式。那些属于 PRD 和 Spec 的范畴

一个常见的失误是把 PB 写成 PRD 的缩写版，塞入大量功能描述。CTO 读完后会问：“所以你要我批人、批钱的理由到底是什么？” PB 必须先独立回答这个问题

在评估一个提案时，底层逻辑可以收敛为五个问题：Why（为什么现在做）、What（做成什么算赢）、How（工程上怎么走通）、How much（要多少资源）、What if（最危险的情况是什么、怎么兜底） 。PB 的结构应当直接对应这五个问题，而不是按“背景—功能—排期”的流水账展开

## Why —— 用业务损失和窗口期说话

开头要写为什么做这个

开头不要写“随着业务发展……”。老板需要看到的是不做的代价，而不是做的理由。有效的写法是业务痛点 + 数据佐证：当前什么指标在恶化、影响了多少用户/收入/效率、如果不解决，未来 3—6 个月会恶化到什么程度

同时要回答为什么是现在：是外部窗口期在关闭，还是内部某个依赖即将就绪？没有时间压力的提案，在 CTO 的优先级排序里天然靠后

## What —— 目标是可验证的终点，不是口号

“提升系统性能”“优化用户体验”不是目标。PB 中的目标必须经得起上线后的验证。用 SMART 原则写一句核心目标，例如：“在 Q2 结束前，将 X 接口的 P99 从 2.3s 降至 800ms 以内，可用率不低于 99.99%”。CTO 需要的是“白纸黑字写下来、事后能对账”的终点

如果目标涉及多个维度，控制在 2—3 个核心指标以内。指标越多，越说明没想清楚什么最重要

**也就是说，一定要考量这个东西如何验收**

## How —— 展示工程路径的“骨架”，而不是功能皮肤

这是 PB 中最容易写偏的部分。CTO 不需要看到每一个按钮，但需要看到系统边界、关键模块的职责、核心数据流向，以及技术选型的理由——尤其是“为什么不选另一个”，重点在于**屏蔽技术细节**

一个有效的极简写法：用一张高层架构图（或文字描述的模块关系）+ 三句话说明选型逻辑。例如：“初期用成熟 API 快速验证，核心壁垒在数据和场景而非模型本身；数据规模达到 X 后切换为自部署方案以降本。”关键不在于图多漂亮，而在于让 CTO 看到你对“工程上怎么走通”有过严肃思考

同时要明确 MVP 的边界：第一版做什么、明确不做什么。CTO 对“什么不做”的重视程度，往往高于“做什么”

## How much —— 资源是“投资”，不是“要人”

资源需求不能只写“需要 5 个后端、2 个前端”。CTO 需要看到的是资源与产出的对应关系。建议用一张简表呈现：阶段、所需角色与人数/人月、主要交付物、大致时间窗口。如果有外部成本（云资源、API 调用、软件许可），单独列出量级

一个容易被忽略但 CTO 会立刻注意到的问题是：这些人从哪里来？是从现有项目中抽调，还是新增编制？抽调对现有交付的影响是什么？主动交代这一点，会显著提升提案的可信度

## What if —— 主动暴露风险，而不是等 CTO 来问

CTO 的职责要求他优先考虑风险和成本。在 PB 中主动、具体地列出 2—3 个最关键的风险及其缓解措施，是建立技术信任的最快方式。风险要写得具体可感，不要写“存在技术风险”这种空话

有效的风险描述包含三个要素：风险场景 → 可能后果 → 缓解或兜底动作。例如：“若核心 API 的调用成本超出预期，MVP 阶段按用户设置每日上限，并监控 Token 消耗，超阈值时降级到轻量模型处理非关键任务。”如果存在回滚方案，务必写明——CTO 会特别关注方案失败后能否安全退回
