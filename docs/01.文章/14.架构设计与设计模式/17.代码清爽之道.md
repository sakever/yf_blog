代码写出来是给人看的，顺便能在机器上运行。同样一个功能，有人写出来三百行全是重复劳动，有人写出来八十行每一行都有存在的必要，两者的维护成本天差地别

清爽的代码只有一个核心原则：**尽可能复用，不要臃肿**。围绕这个原则，在实际写代码时落地为下面几条规则

## 转换逻辑写在 POJO 中

`fromProtobuf`、`toProtobuf` 或者抽取资源列表这类转换逻辑，写在对应的 POJO 类中，满足充血模型

```java
public Common.Vector3 toProtobuf()
{
    return Common.Vector3.newBuilder()
            .setX(x)
            .setY(y)
            .setZ(z)
            .build();
}

public List<String> getResourceList() {
    List<String> ret = Lists.newArrayList();
    if (StringUtils.hasLength(coverResourceID)) {
        ret.add(coverResourceID);
    }
    if (StringUtils.hasLength(videoResourceID)) {
        ret.add(videoResourceID);
    }
    if (StringUtils.hasLength(videoCoverResourceID)) {
        ret.add(videoCoverResourceID);
    }
    return ret;
}
```

为什么需要这么做？如果转换逻辑写在 Service 或者某个 Util 里，随着字段增加、调用方增加，同一个 POJO 的转换代码会散落在项目各处，改一个字段要全局搜索半天，还容易漏改。充血模型把"数据 + 与数据强相关的行为"放在一个类里，**找到 POJO 就能找到所有和它相关的转换**，新增字段时只需要改这一个类，所有调用方自动受益

贫血模型不是不能写，而是它把本该内聚的逻辑推给了调用方，调用方一多，重复代码就指数级增长

## 工具类优先，禁止重复造轮子

涉及字符串转换的逻辑写在 `StringUtil` 中、时间戳转换相关的逻辑写在 `DateUtil` 中、json 相关的逻辑写在 `JsonUtil` 中，以此类推。**相关的转换逻辑在写之前，先看看对应的工具类有没有现成的方法**

这条规则针对的是最常见的隐性重复：同一个"时间戳转 yyyy-MM-dd"在项目里出现了五种实现，有的带时区有的不带，有的判空有的不判，出 bug 的时候你根本不知道线上跑的是哪一种

先查工具类再动手，查不到再往工具类里加方法，而不是在业务代码里现场写一段。工具类就是团队内的"轮子仓库"，它的价值在于**同一个语义全项目只有一份实现**

## 尽可能使用 Lombok

不要手写一堆 get 和 set 方法，推荐使用 `@Data`、`@Builder` 等注解

```java
@Data
@Builder
public class PlayerInfo {
    private long playerId;
    private String nickname;
    private int level;
}

// 使用 Builder 构建，字段含义一目了然
PlayerInfo info = PlayerInfo.builder()
        .playerId(10001L)
        .nickname("yifan")
        .level(30)
        .build();
```

手写 getter/setter 一是没有信息量，纯粹的噪音代码；二是字段重命名时容易漏改某个 getter。`@Builder` 相比构造函数传参的优势在于**参数是具名的**，`new PlayerInfo(10001L, 30)` 这种连续同类型参数的调用，一旦顺序写反编译器不会报任何错

## 深拷贝使用构造函数

涉及深拷贝的场景，使用拷贝构造函数来处理

```java
public UgcVector3(UgcVector3 v)
{
    if (v == null) {
        return;
    }
    x = v.getX();
    y = v.getY();
    z = v.getZ();
}
```

为什么不用 `clone()`？`clone()` 是 Object 上一个设计失败的方法：它是浅拷贝，不调用构造函数，子类忘了重写就会出现灾难性的对象共享，Effective Java 里直接建议避免使用

拷贝构造函数把"复制这个对象"的逻辑收拢在类内部，引用类型字段该深拷贝还是共享，由类自己决定，调用方无感知。字段增加时也只需要改构造函数这一处

## 注释不要留空行

注释（Javadoc）中不要用空行分段，使用 `* <p>` 来分隔段落

```java
/**
 * 计算玩家的战斗力。
 * <p>
 * 战斗力由基础属性和装备加成两部分组成，
 * 装备加成需要先经过洗炼系数修正。
 */
public int calcBattlePower(Player player) {
    ...
}
```

为什么？Javadoc 生成文档时会把连续的文本合并成一个段落，注释里的空行会被直接吃掉，多段说明挤成一坨。`<p>` 是 HTML 的段落标签，是 Javadoc 官方认的分段方式，**注释在源码里和生成的文档里都能保持正确的分段结构**

## 接口入参必须使用 DTO

接口中 `@RequestBody` 需要使用 DTO 来接收，不准用 Map；`@RequestHeader` 需要使用就接受，不需要就不用接受；HttpServletRequest 同理

```java
// 反例：Map 接参，调用方和被调方全靠猜
@PostMapping("/update")
public Result update(@RequestBody Map<String, Object> params) {
    long playerId = (Long) params.get("playerId");
    ...
}

// 正例：DTO 接参，字段类型、是否必填一目了然
@PostMapping("/update")
public Result update(@RequestBody UpdatePlayerRequest request) {
    ...
}
```

Map 接参的问题在于**它没有 schema**：字段叫什么、什么类型、能不能为空，全部藏在方法体里。接口文档没法自动生成，调用方靠看源码猜字段，强转类型失败运行时才爆炸，参数校验也没地方挂（DTO 上一个 `@Valid` 加 `@NotNull` 就解决了）

`@RequestHeader` 和 `HttpServletRequest` 则是反向要求：用不到就不要声明，每个多余的参数都是对方法签名的污染，也会误导后来人以为这个接口依赖了请求上下文

## 使用统一的判空方法

使用 `StringUtil.isNullOrEmpty`、`CollectionUtils.isEmpty` 等方法来判空，不要手写 `str == null || str.isEmpty()`、`list == null || list.size() == 0`

```java
// 反例：判空条件散落各处，风格不一，容易漏
if (name == null || name.isEmpty()) { ... }
if (list == null || list.size() == 0) { ... }

// 正例：一个方法表达一个语义
if (StringUtil.isNullOrEmpty(name)) { ... }
if (CollectionUtils.isEmpty(list)) { ... }
```

手写判空的第一个问题是容易漏：判了 null 忘了空串，忘了 trim 之后全是空格的串。第二个问题是语义不统一：`isNullOrEmpty` 一眼能读出"无值"这个业务语义，而一长串 `||` 条件需要逐个读过去才能确认意图。判断逻辑内聚在工具方法里后，**"什么算无值"这个定义全项目只有一份**，将来要改（比如把全空格也算无值），改一处即可

这些规则看起来都是小事，但代码的清爽感正是由这些小事堆出来的：转换逻辑有固定的位置、工具方法先查再写、样板代码交给注解、判空有统一的语义。新人接手时不需要读完整个 Service 才能理解一个转换，改字段时不需要全局搜索五处散落的实现——这就是复用带来的直接回报
