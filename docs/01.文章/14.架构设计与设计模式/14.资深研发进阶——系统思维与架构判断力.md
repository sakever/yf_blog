一个菜鸟后端开发工程师进阶到资深开发的评判标准之一就是是否拥有工程化思维，因此这篇博文总结一下工作时的常见技术问题，以及资深研发应该如何考虑一个需求

## 系统思维
首先是迈入架构师的第一步：培养系统思维。开发者思维只停留在我的代码能跑吗这一问题上，架构思维会问这个组件在整个生态里表现如何

具体来说首先每次技术决策时，强迫自己补全这句话：**遇到 X 问题，选型有 ABC，他们分别擅长 XYZ。在该场景下我们选择 A，是因为它能带来 X，同时我们接受 O 这个代价**

这里的 X 问题可能是线上问题，你需要调研清楚问题边界、具体问题定义和影响等等；选型需要搜索各大开源方案，现在 AI 也很优秀可以帮忙收集；最后的判断一定不是选择了最好的方案，而是在最适合当前场景的方案，同时方案会带来各种问题和代价，我们接受并且确认影响面较小

**在技术决策落地后，你需要使用数据说话，其选型最后的收益是什么**

更加进阶一点，你需要思考：**系统会朝哪个方向演化、哪里会出现瓶颈、什么样的设计能活过下一次需求变更**

## 非功能性需求——NFRs
之前我收集过需求需要考虑的各种额外问题，后来发现他们有一个统一的名字叫 NFRs。NFRs 指非功能性需求。ISO/IEC 25010 提供了一个权威的经典骨架，而云原生和现代工程实践则补充了运维、成本、可观测性等关键维度

NFR 所考虑的是做一个系统，在实现功能后常常会遇到以下情况，这种时候需要考虑这些情况是否需要处理，对业务影响是什么（每个业务所需要考虑的侧重点不同，不用将所有的问题都考虑清楚，但是需要考虑对系统影响最大的问题）
### 性能问题
系统在特定条件下使用资源的表现。子维度包括：
- **时间行为（响应时间、吞吐量、量级）**：判断动作是否需要异步处理，比如使用消息队列削峰填谷等；是否需要批量操作；是否需要使用缓存等等
- **资源利用率（CPU、内存、网络带宽的占用）**：是否需要使用缓存，减少数据库压力；是 IO 密集还是 CPU 密集型；峰值请求过来会占用多少 CPU 和内存资源
- **容量（系统能承载的最大负载）**：需要考虑的负载如如用户量、数据量、请求量等，并为资源规划提供依据。需要考虑峰值和平均量下系统是否可以正常应对（一般来说流量出入口都需要考虑），提供预计响应时间下的响应。典型约束如：“在预期负载下，P95 响应时间不超过 2 秒”

### 可靠性（高可用）
系统在指定条件下维持运行的能力。子维度包括：

- **可用性**：系统可用的时间比例
-- **单点故障**：识别并消除系统中的单点，所谓单点是指这个组件如果失败，会导致整个系统失败，因此需要引入冗余组件，不只是一个机器可能会挂机，可能一个机房也会挂机
-- **故障转移**：主从切换、故障检测与自动恢复机制，可以参考心跳检测、gossip、一致性协议（选主）、故障转移策略这个流程来处理
- **韧性 / RPC 高可用设计**：熔断、限流、降级、超时、负载均衡、失败策略（重试、快速失败、访问集群中其他机器等等）
- **容错性和可恢复性**：考验系统故障时维持功能的能力以及故障后恢复数据与状态的能力。常见的场景是异步流程中如果机器挂机，数据丢失怎么办，可以使用如消息队列持久化、定时任务重试等

### 扩展性
系统在负载增加时，通过增加资源来维持性能的能力。实践中通常要求系统能水平扩展且扩容后性能不退化

- **水平扩展能力**：无状态设计、数据分片策略、nacos zk spring cloud 所涉及到的负载均衡和注册中心相关技术，这是系统可扩容保证
- **单机功能扩张**：适应性、可安装性、可替换性，优秀的系统应该可以提供像接入 mod 一样的扩张能力。一般靠策略、工厂等设计模式实现

### 数据一致性和原子性

- **原子性保证**：业务中某个操作是否需要完整执行或完全回滚
- **分布式一致性**：多节点间数据同步的一致性模型选择（强一致、最终一致等）
- **中间态数据不一致**：需要考虑业务场景中，中间态时数据不一致是否对业务有影响
- **双写一致性**：系统迁移或灰度时双写场景的数据同步问题，需要考虑数据丢失的风险，是否需要采用事务型双写或异步双写，数据迁移时如何保证平滑切换
- **单机、DB、分布式事务管理**：跨服务、跨数据库的分布式事务处理，是否引入 seate 框架，选用何种模式（AT、TCC、SAGA 等），事务执行过程中数据对其他事务是否可见
- **顺序保证**：是否需要保证消息顺序性、操作顺序性
- **并发控制**：是选用乐观锁、悲观锁、分布式锁还是其他方案比如 MVCC、演员模型，具体落地是使用那种技术或者框架

### 引入 X 组件导致其他可能的问题
有些时候我们为了解决某个问题会引入某项技术，而引入这个技术又会出现其他问题

- **数据去重**：如何防止重复写入或重复消费，一般可以使用分布式锁+表内唯一索引来实现
- **缓存策略**：缓存层级、缓存更新策略、缓存穿透/击穿/雪崩等分布式缓存常见问题如何处理
- **数据库性能**：是否需要索引设计、查询优化、读写分离

### 可观测性与可运维性
通过系统的外部输出来推断内部状态的能力。通常围绕三大支柱构建：日志（Logging）、指标（Metrics）、链路追踪（Tracing）

- **日志、监控、告警**：日志级别、日志聚合、链路追踪的 TraceID、核心指标监控（QPS、延迟、错误率）、告警阈值设置、分布式调用链跟踪
- **灰度发布**：流量控制、快速回滚能力；需要考虑向前向后兼容、接口版本管理
- **故障演练**：混沌工程（通过主动注入故障来验证系统韧性的实验性方法）、灾难恢复演练、事先定好故障预案等

### 举例：数据存储与访问
说了这么多，在设计系统时如何考虑这些非功能需求呢，我们以设计新建一张表时需要考虑什么来举例说明

- **rt 优化**：索引、分库分表、缓存等方案
- **分库分表**：分片键选择、是否需要考虑扩容方案、跨片查询（一般是存到 es 中）
- **冷热数据分离**：归档策略、存储成本优化
- **数据备份与恢复**：考虑备份频率、热备冷备、恢复时间目标（RTO）、恢复点目标（RPO）
- **多数据源管理**：数据源路由、读写分离的延迟处理
- **大数据量处理**：后续如果量级是瓶颈的话，需要考虑分页策略、游标方案
- **容量规划**：流量预估、资源评估，可以参考历史业务做判断

## 遇到线上问题时
遇到线上问题时，如果不是你负责的项目，可能无法很快定位问题，因此一个资深研发会遵循以下 SOP，来快速处理问题

1，如何发现问题
- 系统的监控指标和日志，如 CPU 占用率、内存占用率、请求响应时间等，是否存在异常
- 用户反馈、营运同学、合作方告知有异常发生。出现这种情况，说明系统可观测性做的不好，理论上我们应该在用户之前感知到这个问题

2，如何定位问题

理论上我们应该先定位后止损，但是也存在长时间问题定位不到的情况，这时候需要根据具体情况来判断是否需要紧急处理。一般问题都是根据日志、监控、报警来定位的，这就需要考虑一个系统的可观测性做的是否完善。一个系统的可观测性是根据日志、追踪、度量来评估的

3，如何止损

- 第一时间通知相关人员、上级，告知问题发生，询问是否需要紧急处理
- 如果线上需要很快处理问题，请在下面几种方法中选择一个来紧急处理：**重启、扩容、关开关、回滚、摘流、改脏数据**

4，如何修复

改代码重新上线，根据监控系统、数据库、QA 测试等方式确认问题是否解决

5，扩展分析

需要横向比较一下，所负责的系统中是否存在其他类似问题。比如线上出现问题是，锁粒度太大了，你就需要考虑整个系统中是否有其他地方所使用的事务锁粒度大，是否可以优化一下项目中所有锁的粒度
