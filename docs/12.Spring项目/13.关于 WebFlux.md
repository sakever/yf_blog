## 特性
Spring WebFlux 是 Spring 5 引入的响应式 Web 框架。它并非要取代 Spring MVC，而是提供了一种全新的、适用于特定场景的架构选择。其核心特性可以概括为：

1，完全非阻塞（Fully Non-blocking）：这是 WebFlux 的基石。与传统的一个请求一个线程不同，WebFlux 基于事件循环（Event Loop） 模型。它用少量（通常与 CPU 核心数相当）的线程就能处理成千上万的并发连接

2，响应式流与背压（Reactive Streams & Backpressure）：WebFlux 实现了 Reactive Streams 规范，其核心是背压（Backpressure） 机制。这允许数据消费者（Subscriber） 根据自身处理能力，主动向生产者（Publisher） 反馈需求，控制数据流速，防止系统被过载的数据流压垮

3，事件驱动与函数式风格（Event-Driven & Functional Style）：WebFlux 基于事件和回调机制处理数据流。它支持两种编程模型：一种是兼容 Spring MVC 风格的注解驱动模型；另一种是更轻量、更灵活的函数式端点模型

WebFlux 提供了一套完整的响应式工具链，主要包括 Mono（表示0 或 1 个元素的异步序列，常用于返回单个结果）和 Flux（表示0 到 N 个元素的异步序列，常用于返回集合或数据流），Reactive WebClient 一个非阻塞的 HTTP 客户端，用于进行异步、流式地调用外部服务，是 RestTemplate 的响应式替代品

WebFlux 可以运行在多种支持非阻塞 I/O 的服务器上，如 Netty（默认）、Undertow，以及 Servlet 3.1+ 容器
## 使用场景
WebFlux 的优势在于高并发、I/O 密集型的场景，主要有以下几类：

- 高并发微服务与 API 网关：作为微服务架构中的网关（如 Spring Cloud Gateway），需要聚合和转发大量下游服务的请求。WebFlux 的非阻塞特性可以显著提升整体的吞吐量
- 实时数据流应用：例如股票行情推送、实时日志监控、物联网（IoT）数据采集等，需要处理持续不断的数据流
- 长连接与流式响应：需要处理大量 WebSocket 长连接或使用 Server-Sent Events (SSE) 进行流式数据推送的场景
- 异步、非阻塞的集成：当你的技术栈已经全面响应式（如使用 R2DBC 等非阻塞数据库驱动）时，WebFlux 能实现端到端的异步管道

由于学习难度和随着 Java 虚拟线程 的成熟，对于绝大多数新的 Web 应用，使用 Spring MVC + 虚拟线程能在保持代码简单、直观的同时，获得与 WebFlux 相当的性能
## 原理
很多开发者误以为Flux返回数据是一边算一边发，其实流式的核心不在于算，而在于写。它的原理基于 HTTP 分块传输编码（Chunked transfer encoding） 或 HTTP/2 的 DATA 帧

具体流程拆解：

1，Controller 返回 Flux<T>：Spring 发现返回值是响应式流，不会立即把数据序列化成一个大 JSON 数组
2，订阅发生：WebFlux 底层（Netty）会订阅这个 Flux
3，按需请求（背压）：Netty 的 I/O 线程通过 request(n) 信号向 Flux 拉取数据（默认是一次拉取 256 个元素，通过 prefetch 控制）
4，逐块序列化与写入：当 Flux 发射第一个元素时，Netty 会将其序列化为 JSON（或 SSE 格式）。关键点在于 Netty 不会等待所有元素都序列化完，而是立即将这一块数据通过 TCP Socket 写入网络缓冲区（Write-and-flush）。写入动作是非阻塞的，Netty 的 EventLoop 线程写完就立即返回，去处理其他请求
5，重复直至完成：每发射一个元素，就重复序列化 -> 写出的过程，直到 Flux 发出 onComplete 信号，关闭响应流

传统 MVC 必须先把整个 List 全部查出来，塞进内存，一次性序列化成巨大的 JSON 字符串，再一次性写入 OutputStream。Flux 则是边生成边写，内存占用极低，且客户端能尽早收到首字节

特别说明：如果返回的是 Flux<T> 且未指定 produces = MediaType.APPLICATION_NDJSON_VALUE 或 TEXT_EVENT_STREAM_VALUE，Spring 默认会启用分块编码（Transfer-Encoding: chunked），浏览器/客户端会收到一个个独立的 JSON 块

注意 WebFlux 的这套流程需要部署在 Netty 服务器上（默认就是），如果是 tomcat 的话还是和普通的 MVC 没区别

底层栈：Spring WebFlux -> Reactor Netty（封装了 Netty） -> Netty's WebSocketHandler。

当你在 WebFlux 中使用 WebSocketHandler 时，Reactor Netty 会将底层的 TCP 连接升级为 WebSocket 协议，并通过 Netty 的 EventLoop 来处理 WebSocket 帧（Text/Binary/Ping/Pong）。

注意：如果你把 WebFlux 应用部署在传统的 Tomcat（Servlet 容器）上，那么 WebSocket 走的就是 Tomcat 的 WebSocket 实现（基于 javax.websocket），但这会退化为同步阻塞模型，丧失 WebFlux 的优势。所以生产环境用 WebFlux + WebSocket，必须用 Netty 作为内置容器
## WebClient

这个是访问其他项目的客户端工具

WebFlux 只能保证服务端异步响应，但是客户端还是可以同步去访问的。如果希望客户端异步获取数据，那么需要使用异步的客户端。只要使用了异步的客户端，同步的接口也能进行异步访问
