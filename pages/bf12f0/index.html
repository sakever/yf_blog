Actor 模型

演员模型，编程的重点不在线程，而在一个个 Actor 演员，其核心原理在于用串行化的方式去除对锁的依赖。在聊他的技术细节之前，先说一下为什么需要 Actor

# 痛点

在在游戏后端开发中，使用 MVC 模式并非绝对不行，但它确实不是一个理想的选择。因为游戏业务的独特性，当触及游戏的核心逻辑，大多数游戏需要实现高频交互、实时性和复杂状态管理这些场景，比如 mobo，放个技能、移动都需要实时同步，MVC 的局限性就变得非常明显

1，游戏服务器需要维持长时间的 TCP/WebSocket 连接，主动向客户端推送状态更新。而 MVC 本质是同步、阻塞的请求-响应模型，难以处理海量长连接和全双工通信

2，高并发下，MVC 通常基于共享内存模型，开发者需用锁等机制保护数据，易出错且影响性能。而游戏更青睐 Actor 模式那种无共享、通过消息传递的并发模型。因为玩家的移动、攻击等等操作，需要在服务器实时结算并且返回

3，那有没有一种方式，从根本上消灭共享内存、消灭锁，让并发变得可预测，同时将节省下来的性能完整的转换到处理业务逻辑的速度中

有的兄弟，有的，就是 Actor 模型

# 原理

Actor 演员模式是著名的并发设计模式，核心逻辑为不要通过共享内存来通信，而要通过通信来共享数据。它将一切计算单元视为独立的 Actor。每个 Actor 有自己的状态和行为，并且只能通过异步消息与其他 Actor 通信

这不是什么新概念。1973年，Carl Hewitt 就提出了 Actor 模型。后来 Erlang 把它用到了电信系统中（爱立信的 AXD301 交换机，号称99.9999999%可用性——9个9）。如今，Akka（JVM）、Microsoft Orleans（.NET）、Ray（Python）等框架都在用 Actor 模型驱动大规模分布式系统

Actor 模式之所以能解决并发难题，基于以下三条铁律：

1，万物皆 Actor：系统中一切事物（玩家、房间、排行榜）都是一个独立的 Actor

2，通信靠消息传递：Actor 之间绝对不能直接调用对方的方法或修改对方的数据。它们只能通过发送不可变的异步消息来沟通，这彻底告别了共享内存和锁。这和传统 MVC 不一样，你无法直接操作 Actor 对象，只能通过 ActorRef 给它发消息，这是一种强制的隔离。tell 给 Actor 是异步非阻塞的发后即忘，ask 会等待回复，常用于请求-响应模式

3，处理是单线程的，有顺序性的：每个 Actor 内部维护一个先进先出 FIFO 的线程安全的队列，收到的消息会排队。Actor 一次只处理一条消息，且处理过程是在自己的线程（或任务）里顺序执行的，Actor 在创建时会定义好处理消息的逻辑（比如处理攻击或移动消息）。状态（State）是 Actor 内部的私有变量，只有当前处理消息的这段逻辑才能修改它。这意味着，对于单个 Actor 内部，你永远不需要加锁，因为它本身就是线程安全的

他的线程安全的保证，可以举个例子来看。假设我们有10000个玩家 Actor，底层的线程池可能只有8个线程

调度器会轮询这10000个 Actor 的信箱。当发现 Actor-A 的信箱有消息时，调度器会从线程池中抓取一个空闲线程，让该线程处理Actor-A的消息。在处理过程中，如果又来了一条给 Actor-A 的消息，这条新消息不会被当前线程立即处理，而是被放入 Actor-A 的信箱尾部排队

当前线程处理完 Actor-A 的这条消息后，就会释放掉 Actor-A，转而处理其他 Actor 的消息

因此同一时刻，永远只有一个线程在处理特定 Actor 的消息。因此，你在编写单个 Actor 的逻辑时，完全不需要写 synchronized 或 ReentrantLock，这从根源上杜绝了死锁和竞态条件

# 踩坑

Actor 模式最常见的坑点就是做阻塞 IO 导致消息堆积

比如游戏服务器，每个玩家是一个 Actor。其中有一个 Actor 负责存档，当玩家下线时发送 save 消息，这个 Actor 收到后直接调用 write_to_database ——这是一个同步阻塞操作。由于保存操作非常耗时间，那么执行该操作的线程就没有办法执行下一个 Actor 的操作了，导致其他玩家的存档请求延迟飙升

这也是 Actor 的核心缺点，Actor 模型的核心假设是消息处理是快速的。一旦某个 Actor 被阻塞，它会严重影响该系统中所有玩家该功能的响应时间

那么如何处理这种问题呢：

1，将阻塞 IO 委托给专门的异步 Actor 或线程池：Save Actor 收到消息后，将 IO 任务提交给后台线程池，自己立即返回。IO 完成后通过回调消息通知

2，Mailbox 设置背压（Backpressure）：当 Mailbox 超过阈值时，拒绝或丢弃低优先级消息

3，超时+重试：给数据库操作设置超时，避免无限阻塞

一般来说如果是自己手写的 Actor 也需要保证消息投递的可靠性，就是该消息一旦发出，目标一定会收到并且执行完毕，如果报错了就需要将该任务做一些重试、通知、告警等等处理

在 Actor 模型中，消息是不可变的（Immutable） 数据载体。我们用 record 来定义：

// PlayerActor 可能收到的指令消息
public record AttackCommand(String targetId, int damage) {}
public record MoveCommand(int deltaX, int deltaY) {}

// 查询或响应的消息
public record GetHealthQuery() {}
public record HealthResponse(int health) {}

玩家 Actor 是核心，PlayerActor 必须继承自 AbstractActor

import akka.actor.AbstractActor;
import akka.actor.Props;

public class PlayerActor extends AbstractActor {

    // 1. 私有状态（线程安全）
    private int health = 100;
    private int posX = 0;
    private int posY = 0;

    // 2. 静态工厂方法，用于创建 Props
    static public Props props() {
        return Props.create(PlayerActor.class, PlayerActor::new);
    }

    // 3. 定义消息处理逻辑 (核心)
    @Override
    public Receive createReceive() {
        return receiveBuilder()
                // 处理攻击命令
                .match(AttackCommand.class, cmd -> {
                    System.out.printf("[%s] 收到攻击: 目标=%s, 伤害=%d%n",
                            self().path().name(), cmd.targetId(), cmd.damage());
                    this.health -= cmd.damage();
                    System.out.printf("[%s] 当前生命值: %d%n",
                            self().path().name(), this.health);
                })
                // 处理移动命令
                .match(MoveCommand.class, cmd -> {
                    this.posX += cmd.deltaX();
                    this.posY += cmd.deltaY();
                    System.out.printf("[%s] 移动到: (%d, %d)%n",
                            self().path().name(), this.posX, this.posY);
                })
                // 处理查询生命值
                .match(GetHealthQuery.class, q -> {
                    // 将结果回复给消息发送者
                    getSender().tell(new HealthResponse(this.health), getSelf());
                })
                // 处理未知消息
                .matchAny(msg -> {
                    System.out.println("[WARN] 收到未知消息: " + msg);
                    unhandled(msg);
                })
                .build();
    }
}

启动系统并发送消息

import akka.actor.ActorRef;
import akka.actor.ActorSystem;

public class GameServerDemo {
    public static void main(String[] args) {
        // 1. 创建 Actor 系统
        final ActorSystem system = ActorSystem.create("GameSystem");

        try {
            // 2. 创建 10000 个玩家 Actor
            //    每个 Actor 都有自己的信箱（FIFO 队列）
            for (int i = 0; i < 10000; i++) {
                system.actorOf(PlayerActor.props(), "player_" + i);
            }

            // 3. 获取特定玩家的引用
            ActorRef playerActor = system.actorSelection("/user/player_1")
                                         .resolveOne(java.time.Duration.ofSeconds(3))
                                         .toCompletableFuture().join();

            // 4. 异步发送消息（fire-and-forget）[reference:2]
            //    消息会进入 player_1 的信箱排队
            playerActor.tell(new AttackCommand("Boss", 10), ActorRef.noSender());
            playerActor.tell(new MoveCommand(5, -3), ActorRef.noSender());

            // 5. 发送请求并等待响应（模拟 RPC）
            //    注意：ask 模式会创建一个临时 Actor 来接收回复
            //    这里为了演示简单，使用同步等待，实际开发应使用异步回调
            java.util.concurrent.CompletionStage<Object> reply =
                akka.pattern.Patterns.ask(playerActor, new GetHealthQuery(),
                                          java.time.Duration.ofSeconds(5));
            reply.thenAccept(response -> {
                if (response instanceof HealthResponse hr) {
                    System.out.println("查询到玩家生命值: " + hr.health());
                }
            }).toCompletableFuture().join();

        } finally {
            // 6. 优雅关闭 Actor 系统
            system.terminate();
        }
    }
}

每个 Actor 自带 FIFO 信箱，所有发往 player_1 的消息（AttackCommand、MoveCommand）都会进入它的专属队列。同时 Akka 的调度器（Dispatcher）会确保任何时候，最多只有一个线程在运行 player_1 的 createReceive() 方法，从根源上避免了锁竞争、死锁等并发问题

# 落地

真实落地时可能还会遇到其他问题，比如 Actor 如何与线程池中的线程关联起来

一般来说我们有很多 actor，可以给每个 actor 赋予一个唯一 ID，然后通过 Math.abs(hostUserID) % count 的方式，将 actor 绑定到一个线程上，或者用其他方式绑定。然后线程执行 actor 中的逻辑，执行完一个 actor 中的所有 FIFO 信箱后才执行下一个 actor

# 总结

Actor 的处理不算特别高明的手段，使用部分串行化来保证消除锁竞争，是在数据变化频繁这一特定场景下的优秀处理方案。但是没有什么方案是完美的，它的设计理论决定了使用它时需要注意 IO 阻塞、异步消息投递、消息丢失等等问题
