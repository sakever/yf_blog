搜推技术

搜推为啥会放到 AI 分类中呢，因为我觉得有很多东西和模型的底层原理都是互通的，都是算法同学去处理，最近几天对这块很感兴趣，所以学习了一下相关知识

# 基础概念

当评估一个分类模型（尤其是二分类模型）的好坏时，经常能看见几个核心指标：精确率、召回率、F1值

精确率是决策正确的比例。在模型所有预测为是的案例中，有多少是真正的是？主要关注模型预测为是时的可信度，高精确率表示模型把握很大才做出阳性预测，最大限度地减少了误报。eg：垃圾邮件过滤器，高精确率表示正常邮件被判断为垃圾邮件的概率很低（此场景下我们关注的是垃圾邮件被正确识别）

召回率关注模型找出所有目标的能力。高召回率表示是模型在尽可能找出所有正例，最大限度地减少漏报

eg：疾病筛查。高召回率表示找出几乎所有患者（高 TP，即使着会导致许多健康人需要二次检查，即高 FP），减少漏掉的可能

我们需要关注精确率与召回率的权衡，精确率和召回率在大多数情况下是互相矛盾的。提高判断标准以提升精确率（减少 FP），通常会导致召回率下降（增加 FN）

反之放宽标准以提升召回率（减少 FN），通常会导致精确率下降（增加 FP）。模型优化常常是在寻找两者之间的一个可接受的平衡点。F1 值指的就是衡量综合平衡能力。F1值 = 2*（精确率 * 召回率）/（精确率 + 召回率）

在对 rag 或者搜推做任何改动之后，一定要 ab 来评估召回率和精准度

同样还有一个著名的概念叫鲁棒性，是 robustness 的音译，在中文中常常也被表达为健壮性、强壮性和稳健性，总体来说其可以用于反映一个系统在面临着内部结构或外部环境的改变时也能够维持其功能稳定运行的能力。例如，一个鲁棒的 NLP 模型应能理解和处理英语、中文、俚语以及网络用语的混合体，即便这些文本远离训练时使用的标准语料库

# 搜推

# 协同过滤

协同过滤 Collaborative Filtering, CF 利用群体智慧进行预测。它又分为基于用户的 CF 寻找与目标用户兴趣相似的其他用户，推荐他们喜欢的物品和基于物品的 CF 推荐与用户历史喜欢物品相似的其他物品。首先要在 UserCF 和 ItemCF 之间做出选择，它们观察的是同一张数据表的不同维度

UserCF 是找兴趣相似的人，把他们喜欢的东西推给你。系统会计算用户之间的行为相似度，找到与你行为重叠度最高的 K 个邻居，然后把他们喜欢、但你还没接触过的物品推荐给你。这种方式适合内容时效性强、用户兴趣发散的场景（如新闻、视频）

至于怎么落地，举个例子，多用户埋点信息匹配，降维、局部敏感哈希（LSH）或近似最近邻（ANN）离线计算

ItemCF 是你喜欢 A，就推给你和 A 相似的 B；计算物品之间的相似度——如果大量用户同时消费了物品A和物品B，那么A和B就被认为是相似的。在电商等物品集相对稳定的场景中有很多应用（落地：用户+物品特征提取，热门物品降权）

核心需要解决的问题：冷启动、数据稀疏性、多路召回并行等

# 基于内容搜推

基于内容的推荐 Content-Based Filtering 是通过分析用户历史偏好物品的内容特征，构建用户兴趣画像，然后推荐与用户兴趣画像在内容上相似的物品。主要构建物品的特征表示 + 用户的偏好画像。它不依赖其他用户的行为，核心问题是如何把物品的内容和用户的兴趣都变成可计算的向量，并在同一个空间里做匹配。这也是目前系统做法，用户和视频加标签并且进行标签匹配，就是糙了点，但其局限在于容易让用户陷入信息茧房

文本特征是工程上最普遍、最基础的来源。绝大多数基于内容的系统，首先要把物品的描述文本转换为关键词向量。经典的 TF-IDF 就是最常用的基线方案：它同时考虑一个词在单个物品描述中的频率（TF）和它在整个物品库中的稀有程度（IDF），从而给有区分度的关键词更高的权重

核心落地步骤是把库里每一个物品都变成一个固定维度的特征向量，然后在物品所处的同一个特征空间里，构造一个代表该用户偏好的向量。最直接的工程做法是对用户交互过的物品特征向量做加权聚合。例如，如果用户对某几部动作片给出了高分，系统就将这几部电影的特征向量（可能包含“动作”、“爆炸”、“孤胆英雄”等维度）按评分加权求和或平均，得到一个代表该用户兴趣的向量。这样，用户画像和物品画像就在同一个向量空间里，可以直接比较。召回直接用余弦相似度、近似最近邻搜索（ANN）即可，要是过多的数据就需要额外优化了

核心需要解决的问题：特征工程质量、无法产生惊喜、无法利用社会证明信号

# 数据层

这一层我们用到了向量数据库相关的知识，但是以下两个知识点确实是搜推中有的

# 语义类数据

语义类数据可能不止包含密集向量，一些标签也可以是语义类数据。举例来说，标题/正文 embedding、图像/视频 embedding、类目语义标签、多模态向量等都是语义类数据

它的来源包含内容理解模型（BERT/CLIP/多模态编码器）、NLP/CV 抽取、知识库。无论物品是否出现在历史交互中，只要它有标题、图像或描述，编码器就能将其映射为一个稠密向量。语义表示不依赖于“是否被见过”，它依赖的是“内容本身是什么”

在搜推中，一般会用内容 embedding 做 ANN 检索，比如 query 语义召回、多模态商品召回、跨域内容召回。它擅长泛化和内容理解，新物品只要内容可编码，就能获得有意义的表示；语义相近的物品可以在表示空间中被识别为“同类”，从而支撑跨域迁移和冷启动。但语义表示的固有风险是同质化：多个内容相似的物品可能被映射到过于接近甚至相同的表示，导致系统无法区分它们。语义相似不等于用户行为相似，两个“看起来一样”的物品，可能吸引完全不同的人群

# ID 类数据

ID 是离散的、高基数的主键符号。一个 item_id 就是一个整数或字符串，它本身不携带任何可计算的语义内容，只作为查表的键存在。它的“含义”完全来自于在训练数据中观察到的共现关系——ID 表是从历史交互中学习出来的，训练时未见过的物品根本不会获得 ID embedding

ID 能精确区分不同物品，即使它们的内容高度相似。但代价是：ID 表完全依赖历史交互，未见过的物品没有 embedding，极低频物品的表示也不可靠，一般来说我们会用语义向量作为初始向量或辅助特征，冷启动然后逐渐训练成 ID 向量

为什么需要 ID 数据呢，因为我们希望通过模型自动学到其他高级特征（比如某个用户喜欢特定品类的商品，或者某些广告容易被点不喜欢，或者某些用户只喜欢看新内容等），这些特征没有任何语义，只能通过模型不断训练出来

# 召回层

召回层是搜推漏斗的第一级，它的产出直接决定了整个系统的效果天花板。召回层的任务是用极低的成本，在亿级池子里尽可能不漏掉用户可能感兴趣的候选，也就是在保证速度的前提下提高召回率，一切技术选择都服务于这个约束

# 多路召回

多路召回是推荐系统、信息检索等领域中的一种常用技术策略，也是工业级标配，核心思想是通过多个不同的召回路径从海量数据中快速筛选出和搜索目标可能相关的候选集，为后续的排序、精排等环节提供基础

比如说，我们需要搜和用户兴趣相关的数据，用户兴趣可能体现在多个方面，单一召回路径难以全面捕捉。比如用户要买东西，我们可能通过用户浏览记录、搜索记录、相似产品等多个维度推荐用户物品。其核心在于用多样性对抗不确定性

BM25 + 向量检索 + RRF 融合是大多数系统使用的多路召回策略，但是多路召回除了稀疏 + 密集两路，还可以纳入知识图谱检索、SQL 精确查询、元数据过滤、多模态检索等更多召回源

BM25 是词法召回，擅长精确串匹配，订单号、商品型号、专有名词这类身份差异而非语义差异的检索，纯语义模型分不清 SO-8842 和 SO-8843，词法分支才能唯一命中

向量检索不必多说，ANN 索引在向量数据库一章中有详细介绍

RRF 处于召回和排序之间的融合层，它的工作是把多路召回各自产出的排序列表拼成一个统一的候选集。一般来说，它只能判断这个文档在多路里是不是都排得靠前，无法判断这个文档到底跟 query 相关不相关

RRF 因其对分数尺度不敏感、对异常值鲁棒，已成为混合召回的常用基线；加权 RRF 在标注数据可用时能进一步带来约 5% 的 nDCG 提升。更精细的融合还会避免纯关键词命中因向量分低而被阈值绞杀，让每一路的最强信号都有机会进入候选池

# 双塔模型

当前主流的嵌入模型通常是基于 BERT 的变体，关于模型的选型上，一般采用双塔模型：Query 和 Document 各自用一个编码器单独处理，最后用向量相似度（如余弦、内积）来评估它们的相关性

这两个塔参数可以共享，也可以不共享，编码器（将文本嵌入）一般是 BERT、MiniLM、E5、BGE 等。这种模型非常适合 rag，可以预先编码文档向量，Query 来时只需要做一次检索，适合大规模检索（粗排），但是无法捕捉 Query 和文档之间的精细交互

双塔作为召回模型时，核心诉求是速度与覆盖。用户塔和物品塔独立编码，物品向量离线预计算并灌入 ANN 索引；在线只需对用户塔做一次前向推理，然后在索引中做近似最近邻搜索。匹配函数通常就是内积或余弦，不需要任何交叉特征。它面对的是亿级候选，延迟要求在毫秒级，精度是“中等”即可——召回层不负责精确排序，只负责把有希望的候选捞进来

# 排序层

排序层涉及粗排和精排，一个搜推流程通常涉及以下步骤，比如用户需要搜索一个有关 ssm 的知识：

1，初步检索：使用快速检索算法（如 BM25）找到与查询相关的初始候选集合（召回） 2，深度学习模型评分：将初步检索结果中的每个文档或段落以及原始查询输入到深度学习模型（如 BERT 或其他 Transformer 模型）中，该模型会为每个文档分配一个相关性得分 3，排序：根据深度学习模型给出的得分，重新排列初步检索结果的顺序，确保得分最高的文档排在前面

# 粗排

粗排的目标不是成为小精排。工业实践表明，精排注重的是头部商品的精细排序，而粗排真正的价值在于腰部商品的筛选能力。把精排模型直接放到粗排阶段去打分，结果会惨不忍睹，大量未见过的样本分数趋向于随机

因此，粗排关注的不是我的排序和精排有多像，而是精排真正需要的那些候选，我有没有漏掉，有没有给它们一个足够靠前的位置

样本选择偏差是粗排优化中最棘手的问题之一。粗排模型在离线训练时，如果只用精排下发的真实曝光样本，那么训练样本空间就只是线上打分空间的一个极小子集，两者分布严重不一致。这会导致模型对大量未曝光过的候选打分失真

粗排需要打分的候选集规模远大于精排，而整个系统的端到端延迟有严格上限。这意味着：

1，粗排模型必须极轻量。双塔结构（用户/查询塔与物品塔分离，物品向量可离线预计算）之所以在粗排中常见，正是因为它能大幅降低在线计算成本

2，任何精度提升的手段（如引入交叉特征、更复杂的网络），都必须先回答一个问题：它带来的收益，是否值得牺牲吞吐或增加延迟？粗排的每一次模型迭代，本质上都是一次精度与性能的 trade-off

# 精排

关于深度学习模型评分和排序，我们有很多方案，最简单的一种是直接用大型语言模型本身来进行重排，只需要一个提示词即可，当然过程中更加优秀的方案是使用交叉编码器，这就引入了一些新知识点：

# 交叉编码器

交叉编码器（Cross-Encoder）非常适合精排，它是 Rerank 阶段常用模型结构，核心是 Query 和 Document 拼接在一起，通过 Transformer 层 token 级别全交叉注意力处理。每个词之间都可以感知彼此的存在，无论它是 Query 词还是 Doc 词。精度最高，因为 Query 和 Doc 的所有 token 之间都能互动，可学习精细的匹配特征（如实体、数字、语法），非常慢，不能预编码，每一对 Query + Doc 都要重新跑一遍模型，不适合大规模检索，只适合精排（Rerank）

因此目前工程上推荐的流程是双塔粗排后让交叉精排

# 反馈层

反馈层是搜推系统里一个容易被低估、但直接决定系统能不能随时间变聪明的环节。它的核心职能不是做推荐，而是把在线服务的产出和用户的反应，转化成下一轮模型可用的学习信号，并驱动画像与策略的刷新。选型的关键，是在信号时效性、实现复杂度、系统稳定性三者之间找到与业务阶段匹配的平衡点

反馈层通常驱动两类动作，这两类动作对技术栈的要求截然不同：

第一类是刷新画像与特征。曝光、点击、加购、下单等结果回流后，实时更新用户短期兴趣向量、物品热度统计、曝光去重记录等。这类动作的目标是让下一次请求就能用上最新的行为信号，延迟敏感度极高，但通常只涉及轻量的状态更新，不触碰模型参数本身

第二类是更新模型参数。用回流的行为数据构造训练样本，驱动召回、粗排或精排模型的学习。这才是反馈层在算法意义上的核心，但它的时效性要求可以很宽——从秒级在线学习到天级批量重训，都合理
