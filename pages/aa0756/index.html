关于 WebFlux 与 WebClient

# 特性

Spring WebFlux 是 Spring 5 引入的响应式 Web 框架。它并非要取代 Spring MVC，而是提供了一种全新的、适用于特定场景的架构选择。其核心特性可以概括为：

1，完全非阻塞（Fully Non-blocking）：这是 WebFlux 的基石。与传统的一个请求一个线程不同，WebFlux 基于事件循环（Event Loop） 模型。它用少量（通常与 CPU 核心数相当）的线程就能处理成千上万的并发连接

2，响应式流与背压（Reactive Streams & Backpressure）：WebFlux 实现了 Reactive Streams 规范，其核心是背压（Backpressure） 机制。这允许数据消费者（Subscriber） 根据自身处理能力，主动向生产者（Publisher） 反馈需求，控制数据流速，防止系统被过载的数据流压垮

3，事件驱动与函数式风格（Event-Driven & Functional Style）：WebFlux 基于事件和回调机制处理数据流。它支持两种编程模型：一种是兼容 Spring MVC 风格的注解驱动模型；另一种是更轻量、更灵活的函数式端点模型

WebFlux 提供了一套完整的响应式工具链，主要包括 Mono（表示 0 或 1 个元素的异步序列，常用于返回单个结果）和 Flux（表示 0 到 N 个元素的异步序列，常用于返回集合或数据流），Reactive WebClient 一个非阻塞的 HTTP 客户端，用于进行异步、流式地调用外部服务，是 RestTemplate 的响应式替代品

WebFlux 可以运行在多种支持非阻塞 I/O 的服务器上，如 Netty（默认）、Undertow，以及 Servlet 3.1+ 容器。虽然部署到普通容器上就失去了它核心功能，但是项目是可以跑的

# 使用场景

WebFlux 的优势在于高并发、I/O 密集型的场景，主要有以下几类：

  • 高并发微服务与 API 网关：作为微服务架构中的网关（如 Spring Cloud Gateway），需要聚合和转发大量下游服务的请求。WebFlux 的非阻塞特性可以显著提升整体的吞吐量
  • 实时数据流应用：例如股票行情推送、实时日志监控、物联网（IoT）数据采集等，需要处理持续不断的数据流
  • 长连接与流式响应：需要处理大量 WebSocket 长连接或使用 Server-Sent Events (SSE) 进行流式数据推送的场景
  • 异步、非阻塞的集成：当你的技术栈已经全面响应式（如使用 R2DBC 等非阻塞数据库驱动）时，WebFlux 能实现端到端的异步管道

由于学习难度和随着 Java 虚拟线程 的成熟，对于绝大多数新的 Web 应用，使用 Spring MVC + 虚拟线程能在保持代码简单、直观的同时，获得与 WebFlux 相当的性能

# 原理

很多开发者误以为 Flux 返回数据是一边算一边发，其实流式的核心不在于算，而在于写。它的原理基于 HTTP 分块传输编码（Chunked transfer encoding） 或 HTTP/2 的 DATA 帧

具体流程拆解：

1，Controller 返回 Flux：Spring 发现返回值是响应式流，不会立即把数据序列化成一个大 JSON 数组 2，订阅发生：WebFlux 底层（Netty）会订阅这个 Flux 3，按需请求（背压）：Netty 的 I/O 线程通过 request(n) 信号向 Flux 拉取数据（默认是一次拉取 256 个元素，通过 prefetch 控制） 4，逐块序列化与写入：当 Flux 发射第一个元素时，Netty 会将其序列化为 JSON（或 SSE 格式）。关键点在于 Netty 不会等待所有元素都序列化完，而是立即将这一块数据通过 TCP Socket 写入网络缓冲区（Write-and-flush）。写入动作是非阻塞的，Netty 的 EventLoop 线程写完就立即返回，去处理其他请求 5，重复直至完成：每发射一个元素，就重复序列化 -> 写出的过程，直到 Flux 发出 onComplete 信号，关闭响应流

传统 MVC 必须先把整个 List 全部查出来，塞进内存，一次性序列化成巨大的 JSON 字符串，再一次性写入 OutputStream。Flux 则是边生成边写，内存占用极低，且客户端能尽早收到首字节

特别说明：如果返回的是 Flux 且未指定 produces = MediaType.APPLICATION_NDJSON_VALUE 或 TEXT_EVENT_STREAM_VALUE，Spring 默认会启用分块编码（Transfer-Encoding: chunked），浏览器/客户端会收到一个个独立的 JSON 块

注意 WebFlux 的这套流程需要部署在 Netty 服务器上（默认就是），如果是 tomcat 的话还是和普通的 MVC 没区别

# WebFlux、WebSocket

WebSocket 是一种通信协议，是 Java Web 应用中做长连接、流式传输的常用手段（此外还有 SSE 等），MVC 和 WebFlux 都支持它。WebSocket 底层用不用 Netty，完全取决于应用部署在哪个 Web 容器上。如果部署在传统 MVC + Tomcat 场景下，每个 WebSocket 连接会占用一个容器的工作线程（Tomcat 的线程池），直到连接关闭。因为 Tomcat/Jetty 的 WebSocket 实现采用的是 1:1 的线程模型

它和 WebFlux 的区别在于，WebFlux 是一个响应式 Web 框架，而 WebSocket 是一种通信协议，和 TCP 差不多。他们可以一起使用，调用链路如下：Spring WebFlux -> Reactor Netty（封装了 Netty） -> Netty's WebSocketHandler

当你在 WebFlux 中使用 WebSocketHandler 时，Reactor Netty 会将底层的 TCP 连接升级为 WebSocket 协议，并通过 Netty 的 EventLoop 来处理 WebSocket 帧（Text/Binary/Ping/Pong）

注意如果你把 WebFlux 应用部署在传统的 Tomcat（Servlet 容器）上，那么 WebSocket 走的就是 Tomcat 的 WebSocket 实现（基于 javax.websocket），但这会退化为同步阻塞模型，丧失 WebFlux 的优势。所以生产环境用 WebFlux + WebSocket，必须用 Netty 作为内置容器

# WebFlux 与虚拟线程

有人说虚拟线程取代了 WebFlux，事实上两者的底层原理和表现形式都不一样，但是虚拟线程确实有不少 WebFlux 的优势，导致 WebFlux 的生存空间大大减少了：虚拟线程用一种更简单、更自然的方式，解决了 WebFlux 试图解决的高并发问题

虚拟线程编写的代码更正常，更易维护。用虚拟线程，你可以像写传统代码一样，一步步地执行数据库查询、调用外部 API，而不用把它们拆成一个个难以追踪的异步链条。这让开发和维护都轻松很多。同时迁移成本低，只需简单配置即可

虚拟线程对生态没有侵入性。你可以继续使用 JDBC、JPA 这些成熟的阻塞式技术，而不用为了 WebFlux 去寻找和适配响应式版本。同时大量基准测试表明，在典型的 I/O 密集型 Web 应用场景中，虚拟线程的性能与 WebFlux 基本持平

虚拟线程的优势在于处理 I/O 等待，对于 CPU 密集型任务（如大量计算），它并没有性能优势。同时它还是同步阻塞调用，因此在处理大量流式数据（如 Server-Sent Events）、长连接（如 WebSocket）或需要端到端背压（Backpressure） 控制的场景下，WebFlux 的响应式模型依然是更专业的选择，因为其事件循环设计让少量线程可以管理多个连接

# WebClient

这个是访问其他项目的客户端工具。WebFlux 只能保证服务端异步响应，但是客户端还是可以同步去访问的。如果希望客户端异步获取数据，那么需要使用异步的客户端。只要使用了异步的客户端，同步的接口也能进行异步访问

如果说服务端 Netty 解决了如何用少量线程处理大量 incoming 请求，那么 WebClient 解决的就是如何用少量线程发送大量 outgoing 请求。WebClient 默认的底层实现并不是 Apache HttpClient 或 OkHttp，而是 Reactor Netty（和我们之前说的服务端 Reactor Netty 是同一套代码），简单说一下原理

当你在 WebClient 里调用 GET() 时，它不会立即去建立 TCP 连接。它会在 Netty 的 EventLoop 线程池中注册一个连接建立的事件（Bootstrap.connect）。这个操作是非阻塞的，connect() 方法调用后会立即返回一个 Mono，而不会傻等着三次握手结束

WebClient 也有连接与线程的解耦功能，服务端的解耦是请求来了，不占用线程等数据。客户端的解耦是我要发请求，但不占用线程等响应

对于传统 RestTemplate（同步阻塞）来说，调用 restTemplate.getForObject() 时会导致当前线程持有连接，进入 Socket.read() 阻塞状态，操作系统挂起该线程，直到服务器把整个 Response 传回来，线程才被唤醒

而 WebClient（异步非阻塞）会调用 webClient.get().retrieve().bodyToMono(String.class)。Reactor Netty 将请求（HTTP 报文）通过 NIO 的 SocketChannel.write 写入内核缓冲区，写入动作极快，瞬间返回。返回一个 Mono（占位符），当前线程（可能是 Tomcat 线程或虚拟线程）立即被释放，回去干别的事（比如处理其他用户的请求）。当服务器处理完毕，数据通过 TCP 传回客户端的网卡时，Netty 的 EventLoop 线程会监听到 OP_READ 事件，将数据读出，并主动去填充（onNext）那个 Mono，触发你的业务回调
